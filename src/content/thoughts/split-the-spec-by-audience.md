---
title: Split the spec by audience, not by completeness
date: 2026-10-03
---

A product spec usually tries to do two jobs at once: convince a human the feature is worth building, and tell a machine exactly how to build it. Those are different documents wearing the same file extension. The functional half ("what this does and why a user wants it") is written in prose for someone deciding whether to approve the work. The technical half ("these are the interfaces, this is the data shape, here's the file it lives in") is written for whoever implements it, and increasingly that's an agent, not a person.

Stuffing both into one spec.md and handing the whole thing to a coding agent is a context-window problem dressed up as a documentation one. The agent doesn't need the stakeholder framing, the user-empathy paragraph, or the business case; none of it changes what code it writes. It needs the contract. Every sentence of mission language it has to read past is a sentence diluting its attention from the part that actually constrains the output, and it's easy for an agent to implement the wrong interface because the right detail was buried under paragraphs of customer-pain framing it didn't need to read.

The fix is two documents, not one: each agent in the pipeline reads only the one addressed to it. A planning agent breaking a feature into tasks wants the functional spec, intent and acceptance criteria and the edge cases a user would notice; an implementation agent wants the technical spec instead, types and endpoints and the directory a new file belongs in, nothing about why a user wants it. A review agent's needs are narrower again: just the diff and the acceptance criteria, since it's checking behaviour against intent rather than re-deriving the architecture. Same feature, several reading lists, none of them padded.

This only works if someone keeps the two specs honest against each other, because splitting them creates exactly the drift problem that stale AGENTS.md files already have: a technical spec that quietly stops matching the functional one it was supposed to implement, with nothing forcing a cross-check. The cheap guard is structural rather than procedural. Put a single line at the top of the technical spec linking back to the functional requirement it satisfies, by ID, and make the review agent's task include confirming that link still holds. That's a much smaller ask than reading the whole functional document every time, and it catches the one failure mode that actually matters: implementation that's internally consistent but has drifted from what was asked for.

None of this is really about agents. It's the same reason a well-run engineering org keeps the PRD and the design doc as separate artefacts instead of one sprawling file: different readers need different detail, and conflating them serves neither. Agents just make the cost of ignoring that lesson visible immediately, because an overloaded context window fails today, in front of you, instead of quietly next quarter when the PM and the engineer turn out to have read the same paragraph and understood two different features.
